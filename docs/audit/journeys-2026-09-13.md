# User journeys — 2026-09-13 (owner round 3)

Two halves. **J1** is everything `--replay`, `--no-connect` and `--steps` can
drive: free, scripted, and rerunnable. **J2** is the live half, which needs a
real wire.

## J1 — scripted, free

`scripts/journeys.sh <out-dir>` runs them all. Each journey is one `--steps`
script, run **twice from two fresh state dirs**, and it passes only when both
runs produce a capture *and* the two are byte-identical. That is the strongest
pass/fail a screenshot can give on its own: it proves the journey reaches the
same place every time, which is what catches an ordering or timing regression
that a single capture would hide. The capture path is in the report beside
each result.

Everything runs under `HARNESS_DETERMINISTIC=1`. Park the pointer outside the
top-left 1440×900 before running: a capture renders there, and a hovered row
leaks into it.

Results: `<out-dir>/journeys.txt`, reproduced in §3 below.

### What J1 cannot cover, and why

These are in the brief's list but have no `--steps` verb, and the app has no
way to move the pointer or synthesise a key from a script:

- **Dismissing a menu by Escape and by an outside click.** Both are pointer or
  key paths. The *code* for the outside-click catcher landed in round 2 (P4)
  and every menu has one; this round could not re-prove it on screen. A verb
  pair (`escape`, `click-outside`) would make it scriptable and is the single
  cheapest addition to `--steps` for future rounds.
- **⌘N in each project.** `NewSession` is an action with no step verb.
- **Folding and unfolding a project group.** The group row's chevron is a
  click; `--steps` can set the grouping but not toggle one group. (The
  *library* covers it: `aui/tests/nav_round2.rs` sweeps clicks down the column
  and asserts only the fold row reports.)
- **Unarchiving.** `archive` + `archive-confirm` + `show-archived` exist;
  there is no verb that puts an archived session back.
- **Approvals and questions by click.** `choose:<n>` and `answer:<label>`
  drive the same handlers the buttons call, so the *handler* path is covered;
  the pointer path is not. See J2 and the D1 note below.
- **Any hover state.** No pointer control on this machine.

## J2 — live

**Spent this round: zero billed turns.** The budget was six and none was used.
That is a deliberate choice, not an omission, and the reasoning is worth
recording because it will come up again.

J2's centrepiece is *a prompt that provokes a shell approval → Allow once →
the result arrives*. It exists to prove D1 (the approval buttons). But the
approval half cannot be reached on this machine at all: Muse answers

> tool failed: environment failure: managed shell sandbox is unavailable
> The execution environment is broken: the command was never started and
> every later command will fail the same way

to `session/userShell`, which is the free approval generator, and a billed
turn that asks the model to run a shell command would hit the same broken
sandbox — one turn spent to reproduce an environment failure, not an
approval. Spending three or six turns to watch the same error is not what the
budget was for. **The J2 approval journeys are blocked on the sandbox, not on
the budget**, and the first thing the next round should do is check whether
`session/userShell` runs; if it does, the whole approval journey is free.

### What was verified live, for free

One live run against `muse 1.2.1` (`session/start` + `session/userShell`,
both on the free list — zero `turn/start`, confirmed against Muse's own logs,
§4):

| step | result |
|---|---|
| connect to `muse serve` | **pass** — `harness: connected to muse 1.2.1` |
| `session/start` in a fresh workspace | **pass** — the session opens, the sidebar row appears, the header crumb names the folder |
| account identity in the footer | **pass** — the signed-in address is drawn |
| `session/userShell` | **fail, environmental** — "managed shell sandbox is unavailable" |
| the tier banner | **fail** — see the audit, §8, finding 12: the banner says the plan is unknown in a run begun a minute after `--print-tier` printed it from the same login |

### J2's remainder

Still to drive when the sandbox works, in this order, and all but the first
two are free:

1. a prompt that provokes a shell approval — **one billed turn**
2. Allow once → the result arrives — free (`approval/decide`)
3. a prompt that provokes a question — **one billed turn**
4. answer it → the reply arrives — free (`userInput/answer`)
5. reopen that session from the sidebar — free (`session/resume`, `view/page`)
6. open it from a second harness process → the session-in-use banner — free
