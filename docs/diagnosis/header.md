# Section A — Header (items Header 1–5)

## Header 1 — Duplicate traffic lights

**Symptom (owner):** "There are duplicate traffic lights. One of it (the one at the bottom layer) feels like an image or a rasterised version."

**Root cause.** The window asks macOS for native traffic lights *and* the shell paints its own set on top of the same corner:

- Native set: `crates/harness/src/main.rs:329-337` builds `WindowOptions` on top of `TitleBar::window_options()`, keeping its `titlebar` (`appears_transparent: true`, `traffic_light_position: Some(point(px(9.0), px(9.0)))` — `/Users/latekaapi/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gpui-component-0.6.0/src/title_bar.rs:68-74`) and only overriding `title`. So AppKit draws the real, glossy lights at (9, 9).
- Painted set: `crates/harness/src/app.rs:1978` (`.traffic_lights(true)` on `app_shell`) and `crates/harness/src/app.rs:1983` (`.traffic_lights(true)` on `sidebar_header`) turn on the aui fallback: three flat 11 px `div`s (`LIGHT_CLOSE/MIN/ZOOM` at `/Users/latekaapi/Projects/agentic-ui/crates/aui/src/shell/header.rs:32-36`, painted at `header.rs:165-175`). The header comment there says it explicitly: "drawn only when the shell paints its own (the gallery card); real windows show the native ones."
- Proof: `docs/diagnosis/shots/header-open.png` shows glossy native lights at the very top-left with a second, flatter set of circles in the sidebar header row underneath.

**Library inventory.** Existing: `sidebar_header().traffic_lights()` (`header.rs:97`), `app_shell().traffic_lights()` (`app_shell.rs:92`, drives rail width `RAIL_WIDTH_WITH_LIGHTS`, `app_shell.rs:156`). Nothing missing — the library already documents the painted lights as gallery-card-only. Fix belongs in **harness**.

**Proposed fix.** In `Harness::render` (`app.rs:1977-1985`) pass `.traffic_lights(false)` (or drop both calls) on `app_shell` and `sidebar_header`, keeping the option for gallery/parity use. gpui API: no new API; the native lights come from the existing `TitlebarOptions` in `main.rs:332-335` (gpui-pre source: `TitlebarOptions { appears_transparent, traffic_light_position, .. }`, cf. `title_bar.rs:68-74`). Size: **S**. Risks: collapsed rail narrows 72 → 48 px (see Header 5); the sidebar-header cell keeps its left padding so nothing else moves. Test: `cargo test --workspace` (no test covers this; eyeball it) plus screenshot `cargo run -p harness -- --replay fixtures/msp/transcript-real.jsonl --theme dark --screenshot docs/diagnosis/shots/header-nolights.png --screenshot-delay 15000` proving one glossy set remains.

**Open questions.** None.

## Header 2 — Header is not draggable, double-click does nothing

**Symptom (owner):** "The header doesn't work like an actual header of a mac app. In any mac app, you can drag the windows by clicking and dragging on the header. Double clicking it can make the window expand the whole size of the screen. Even the agentic-ui demo app that you made works like this, but not the harness."

**Root cause.** Dragging/double-click in this stack is owned by the gpui-kit `TitleBar` *element*, which the harness never renders. In gpui-component (`title_bar.rs:318-360`) the `TitleBar` element arms `should_move` on left `on_mouse_down`, calls `window.start_window_move()` on the next `on_mouse_move`, and maps double-click to `window.titlebar_double_click()` on macOS (`zoom_window` on Linux); `window_options()` (`title_bar.rs:80-94`) additionally sets `app_owns_titlebar_drag: true` so AppKit does not fight it. The gallery renders that element (`crates/aui-gallery/src/gallery.rs:41`, `TitleBar::new()` inside `render_title_bar`, composed in `Gallery::render` at `gallery.rs:215-229`) — that is the "demo app" drag the owner feels. The harness instead renders `app_shell` + the three aui header cells directly under `Root` (`app.rs:1977-2002`) with no `TitleBar` element anywhere; `SidebarHeader`/`CentreHeader`/`RightHeader` renders (`header.rs:150-185`, `262-285`, `335-356`) contain button-click handlers only — no `start_window_move`, no `on_double_click`, no `window_control_area(Drag)`. So press-drag on the harness header hits inert flex rows and stays put.

**Library inventory.** Existing: drag + double-click live in gpui-kit's `TitleBar` element (path above), not in aui; aui header cells deliberately have no drag affordance. Missing: aui offers no "make this header row a drag region" helper — a harness that keeps its custom three-cell header (instead of adopting the `TitleBar` element) needs one. Fix belongs in **both**: harness wires the behaviour; if the pattern repeats, promote a small `aui::shell::drag_region` helper to the library with a gallery entry.

**Proposed fix.** In `Harness::render` (`app.rs:2014-2046`) wrap the header row (the `app_shell` header, or each header cell) with the same three handlers gpui-kit uses: `on_mouse_down(Left)` → arm, `on_mouse_move` → `window.start_window_move()`, `on_double_click` → `window.titlebar_double_click()` (macOS) — gpui API per `title_bar.rs:330-360`; and/or render the aui header cells *inside* a `TitleBar::new()` element as the gallery does. Careful: interactive children (search, toggles, overflow, title rename field) must `stop_propagation`/keep their click priority so drag does not swallow them; `app_owns_titlebar_drag: true` is already set via `main.rs:336`. Size: **M**. Risks: double-click zoom vs rename-field double-click conflicts; drag region overlapping the traffic-light corner must remain clicks. Test: manual drag + double-click on a live `--no-connect` window (cannot be screenshotted — motion, not pixels); regression gate `cargo test --workspace`. Proof screenshot: none possible; record a note that drag was verified by hand.

**Open questions.** None on cause. Behavioural: should double-click zoom or enter title-rename? (Owner asks for zoom; rename is proposed for the overflow menu, so no conflict expected.)

## Header 3 — Collapse-right button, overflow "…" button, dropdown component

**Symptom (owner):** "The collapse right pane button is not required. On clicking the overflow icon — there should be a dropdown [Rename / Fork / Archive]."

**Root cause / current state.**

- Collapse-right button: the centre header's `toggle-right` (PanelRight) icon (`header.rs:284`, wired at `app.rs:1990`) and the right header's `close` X (`header.rs:353`, wired at `app.rs:1996`) both call `Harness::toggle_right`, which is an intentional no-op: `app.rs:2056-2057` ("The right pane is out of scope this phase; the toggle stays wired"), and the keymap slot is likewise a no-op (`app.rs:2026`). `right_open` is initialised `false` (`app.rs:285`), so the pane renders at width 0. Nothing depends on the toggle — safe to remove the buttons.
- Overflow "…" button: `CentreHeader` renders it always (`header.rs:283`) but the harness never sets `.on_overflow(...)` (zero hits for `on_overflow` in `crates/harness/src/`; the gallery does not set it either). The `ghost()` helper without a handler (`header.rs:140-145`) renders an inert button — today it does nothing. Rename exists via `/name` + row pencil (`sessions.rs`, `app.rs:1130+`); fork exists via turn action + `PaletteKind::Fork`; archive does not exist (hide without confirmation is the closest, `Command::Hide`).
- Dropdown component: aui offers (a) `aui::overlay::popover_layer` (`overlay/mod.rs:44-60`, priority `POPOVER_LAYER = 1`) — the required wrapper; (b) the generic menu `aui::nav::view_menu` + `MenuRow` (`nav/view_menu.rs:68-90`, 250 px menu used from the sliders icon, gallery usage at `cards/views.rs:468`); (c) composer-anchored `model_menu`/`effort_menu`/`mode_menu` (`composer/pickers.rs:135-145`) consumed by `SessionView::render_pickers` (`session.rs:2290-2330`, anchored via `chip_menu` + `popover_layer` at `session.rs:2168-2181`); (d) `command_palette` (`overlay/command_palette.rs:183`). Design rules confirm the overflow menu belongs in the centre header (`agentic-ui/docs/04-design-rules.md:16`).

**Library inventory.** All primitives exist; `view_menu` is the closest fit for Rename/Fork/Archive rows, or a bespoke small menu on the same `menu_surface` chrome (`view_menu.rs:108+`). Missing: nothing structural — possibly per-row enabled/disabled states if Archive needs confirming inline (check `MenuRow` variants at `view_menu.rs:55-65` before designing). Fix belongs in **harness** (wire `on_overflow` → `Overlays::menu` state → anchored `popover_layer(view_menu(...))` + three actions); library only if `MenuRow` cannot express the rows.

**Proposed fix.** In `Harness`: add an `Option<MenuKind>`-style overflow state (or reuse `Overlays::menu` with a new `MenuKind::Session`), set `.on_overflow(...)` on `centre_header` (`app.rs:1987-1995`), render `popover_layer(view_menu(...))` anchored to the header, rows Rename (enter in-place title edit — reuse `start_rename` path used by `rename` step, `app.rs:835-842`), Fork (`fork` at newest completed turn), Archive (new: `sessions.json` flag or extend `hidden` semantics — needs owner decision, see below). Remove `.on_toggle_right(...)` and the right-header `on_close` (keep the `right_open=false` slot). gpui API: `popover_layer` + `view_menu(...).on_activate(...)` per paths above. Size: **M** (L if Archive needs a confirm modal + store migration). Risks: popover anchoring inside the clipping header cell (`overflow_x_hidden`, `app_shell.rs:176`) — anchor like the composer chip menus do; Escape-ordering already centralised (`overlays.rs:131-139`). Test: `cargo test --workspace`; screenshots with palette-style `--steps` verbs if added (`palette`-equivalent for the overflow menu), else manual `--no-connect` capture proving the open menu.

**Open questions.** Archive semantics are undecidable from code: MSP has no archive/delete (`sessions.rs:1-11` — hiding is window-local). Is Archive = hide-in-this-window (reversible, `sessions.json`), or a new cross-host state? Needs owner answer before building.

## Header 4 — Search icon, command palette, full-text search of sessions + created files

**Symptom (owner):** "Clicking the search icon should open the Command Palette. Search should be wired up properly — full text search of all the sessions, search the artifacts/files that we created."

**Root cause / current state.**

- Search icon today: the sidebar header's search ghost button has **no `on_search` handler** set (`app.rs:1981-1985` sets only `on_toggle_sidebar`), so the icon is inert. Search opens only via ⌘⇧F (`FocusSearch` binding, `app.rs:164` → `focus_search`, `app.rs:1278-1283`), which reveals a sidebar filter field (`render_search`, `app.rs:1507-1518`), not the palette. ⌘K opens the palette (`app.rs:2031-2033`), which has three lists — Commands, Resume (session list), Fork (turns) — via `open_palette`/`palette_rows`/`render_palette` (`app.rs:1366-1428`, `1822-1894`), all rendered through `popover_layer` + aui `command_palette`.
- What is indexed, where, how:
  - Sessions: `crates/harness/src/index.rs:75-101` reads Muse's `~/.local/share/muse/session-index.db` **read-only** (`index_path`, `index.rs:58-64`) into `IndexEntry { session_name, title, first_user_prompt, search_text, updated_at_us }` (`index.rs:25-36`). Search matches against `haystack = label + title + first_user_prompt + search_text` (`sidebar.rs:196-215`) with case-insensitive **subsequence** match (`sessions.rs:94-110`). So transcript full text is searchable only insofar as Muse's `search_text` column contains it — the harness never reads transcript bodies itself.
  - Harness's own state under `~/Library/Application Support/harness` (`store.rs:22-28`): `sessions.json` (name/hidden/derived_title, `sessions.rs:52-54`), `history.json` (last 200 prompts per workspace, `history.rs:16-23`) — neither is searched.
  - Created files: **not recorded anywhere**. The only file index is the `@` mention walker: workspace paths (not contents) walked once at boot via `ignore` (respects `.gitignore`, caps at 5 000, `files.rs:22-42`) and subsequence-filtered (`files.rs:51-63`). No content indexing, no artifact registry.

**Library inventory.** Existing: `sidebar_search` frame (`app.rs:1513`), `command_palette` + `PaletteSection/Item` (`overlay/command_palette.rs:161-233`), `model_menu`-family pickers as the anchored-menu pattern. Missing: no full-text search component or file-content indexer in aui — both are app-side data problems, not components. Fix belongs in **harness** (palette wiring + indexing); library only if a new search-result row design is wanted in the gallery.

**Proposed fix.** (1) Set `.on_search(...)` on `sidebar_header` (`app.rs:1981-1985`) to `open_palette(PaletteKind::Commands, ...)` — S. (2) Add a `PaletteKind::Search` list whose rows come from a new `search.rs`: rank `haystack` matches across sessions (weight label > title > prompt), plus `history.json` prompts, plus a content index of created files — which requires first *recording* created files (no such log exists; smallest honest step: index workspace files' contents on demand with caps, or log tool-created paths from the fold). gpui API: existing `command_palette(...)` in `render_palette` (`app.rs:1885`). Size: **S** for (1); **L** for (2). Risks: reading transcript bodies via `session/read` per keystroke is too slow — precompute off-thread with debounce; Muse's `search_text` coverage is unverified (spot-check the db content first). Test: unit tests on ranking (`sessions::matches` pattern); screenshot `--steps 'palette;...'`-equivalent proving search opens from the icon — needs a keystroke/step driver, manual otherwise.

**Open questions.** What counts as "artifacts/files we created" — paths the agent wrote (needs new recording) or all workspace files (walk + content index)? And how much of Muse's `search_text` actually covers transcripts — verify by inspecting the db before promising full-text.

## Header 5 — Traffic lights cut when sidebar collapsed

**Symptom (owner):** "When the sidebar is in the collapsed state — the traffic lights are getting slightly cut."

**Root cause.** Collapsing swaps the sidebar column 252 px → rail width, and the rail is widened to duck under the native lights — but the painted lights are still drawn inside it. Numbers: `SIDEBAR_WIDTH = 252.0`, `RAIL_WIDTH = 48.0`, `RAIL_WIDTH_WITH_LIGHTS = 72.0` (`app_shell.rs:28-42`); `rail_width` picks 72 when `traffic_lights(true)` (`app_shell.rs:156`). Native lights sit at `traffic_light_position (9, 9)` (`title_bar.rs:68-74`), spanning roughly x 9–61. Painted lights start at cell padding 10 + margin-left 2 = x 12 and span 3×11 + 2×7 = 47 px → x 12–59 (`header.rs:20-36`, `165-175`). The two sets overlap almost exactly, and the collapsed cell is `overflow_x_hidden` (`app_shell.rs:176`) with the rail pane clipping (`app_shell.rs:183-194`), so the painted circles stack under the native ones and read as "slightly cut". (Additionally the expand-sidebar affordance moves into the centre header, `app.rs:1991-1993` / `header.rs:251-255`, crowding the same corner.)

**Library inventory.** Existing: `RAIL_WIDTH_WITH_LIGHTS` + the `collapsed()` contract ("Nothing is clipped", `header.rs:107-112`) — the contract is violated by the harness turning painted lights on in a real window. Missing: nothing. Fix belongs in **harness** (Header 1's fix resolves this too: with painted lights off, the 72 px rail holds only empty space under the native lights).

**Proposed fix.** Same as Header 1: `.traffic_lights(false)` in `app.rs:1977-1985`; optionally reduce the collapsed rail toward 48 px once nothing is painted, verifying the native lights (x 9–61) still clear the rail contents. gpui API: none new. Size: **S**. Risks: 48 px rail may collide with the native light footprint — keep 72 px unless a screenshot proves 48 clean. Test: screenshot both states; the collapsed-state capture is currently unscriptable (no `--steps` verb toggles the sidebar — verbs are `search/palette/resume/fork-picker/rename/hidden/empty`, `app.rs:824-852`, plus session verbs in `session.rs`), so add a `sidebar` step verb or take it by hand. Proof: `header-open.png` (open, this report) + a collapsed capture showing intact native lights.

**Open questions.** Collapsed-state screenshot could not be taken: no `--steps` verb drives `toggle_sidebar` (`app.rs:2051-2054`), and `--screenshot` renders one state per run. Recommend adding the verb (one match arm next to `hidden`/`empty`) as part of the fix.
